# FS Kravforvaltning

FS Kravforvaltning viser hele `krav/`-treet i nettleseren og som desktop-app, og oppdaterer visningen straks en `.feature`-fil lagres (parse-feil vises som banner over sist gyldige versjon). Det er en Vite-dev-server med Preact, og en Electron-app. Denne fila beskriver appen og reglene som gjelder når Claude jobber i `fs-kravforvaltning/`. Repoet som helhet er beskrevet i [`../CLAUDE.md`](../CLAUDE.md).

Stiene under er relative til `fs-kravforvaltning/`, bortsett fra `krav/`, `tasks/` og `.claude/`, som ligger i rota av repoet.

## Kommandoer

```bash
npm install
npm run dev
npm run app:dev        # desktop-appen (electron-vite)
npm run app:dist       # pakket desktop-app i release/
npm test               # testene (node --test)
npx changeset          # changeset for en endring i appen (versjon og endringslogg)
```

## Versjon og release

Versjonen styres med Changesets (`.changeset/`). `.github/workflows/kravforvaltning-release.yml` startes bare manuelt, fra `main` (`gh workflow run kravforvaltning-release.yml --ref main`): finnes det changesets, lager eller oppdaterer kjøringen versjons-PR-en (som må lages for hånd første gang, se *Versjons-PR-en* i `docs/release.md`). Når den er merget, kjøres workflowen igjen, og da bygges desktop-appen for macOS (Windows og Linux er kommentert ut foreløpig) og publiseres som GitHub-release `fs-kravforvaltning-v<versjon>` med endringene fra `CHANGELOG.md`. Client ID kommer fra repo-variabelen `KRAV_GITHUB_CLIENT_ID`. En endring i appen som brukerne merker, skal ha en changeset i samme PR. Se `docs/release.md`.

**Spør om release.** Når du har pushet eller laget en PR med en endring i appen som har en changeset, spør brukeren med `AskUserQuestion` om det skal lages en release når endringen er på `main` («Ja, når PR-en er merget» / «Nei, vent med flere endringer»). Er svaret ja:

1. Vent til endringen er merget til `main` (spør brukeren, merge ikke selv). Kjør `gh workflow run kravforvaltning-release.yml --ref main` og følg kjøringen (`gh run watch`).
2. Feiler `version` med «GitHub Actions is not permitted to create or approve pull requests», lag versjons-PR-en for hånd og kjør jobben på nytt (*Versjons-PR-en* i `docs/release.md`).
3. Be brukeren merge versjons-PR-en. Når den er merget, kjør workflowen igjen og følg den til releasen er publisert, eller si fra hvis bygget feiler.

Start aldri workflowen uten at brukeren har sagt ja: en release går ut til alle som har appen, og den oppdaterer seg selv.

## Visningen

Vieweren husker hvor brukeren var (`kravforvaltning:hash` i localStorage), og går tilbake dit når den åpnes uten hash. Det gjelder alltid når desktop-appen starter, og i en ny fane. En fil som er borte, gir forsiden.

`npm run build` lager et statisk bygg i `dist/` med hele `krav/`-snapshotet bakt inn (relative stier, hash-routing). `.github/workflows/deploy-viewer.yml` publiserer det til GitHub Pages (<https://sikt-no.github.io/fs/>) ved push til `main`. I statisk bygg er git-data `null`, så «Endringer»-modusen skjules. HTML-sidene i rota av repoet som står i `STATIC_PAGES` (`src/markdown.ts`, nå `kom-i-gang.html`), legges ved siden av `index.html` i bygget og serveres av dev-serveren (`staticPages` i `vite.config.ts`). Relative lenker til dem i `.md`-filene åpner siden der, og i desktop-appen på GitHub Pages. Tavla «Oppgaver» er alltid med, i dev, i desktop-appen og i bygget (skrivebeskyttet på GitHub Pages): `tasks/` leses og overvåkes alltid, og `tasks/`-snapshotet (`TasksSnapshot`, `virtual:krav-tasks`) bakes inn i bygget. Spesifikasjoner og Oppgaver var to visninger før, og `--mode oppgaver` og `--mode spesifikasjoner` finnes ikke lenger.

## Arkitektur og funksjoner

- `core/` er serverlogikken i ren Node, felles for dev-serveren og desktop-appen: `workspace.ts` (leser, parser og overvåker `krav/` og `tasks/`, og sender `krav:update`/`krav:git`/`krav:tasks`), `api.ts` (kallene rendereren kan gjøre, typene i `shared/api.ts`), `save.ts` (skriver krav-filer, bare `.feature`/`.md` under `krav/`), `auth.ts` (GitHub-innlogging med device flow, eller `gh auth token` i dev) og `vcs.ts` med to git-backender: `vcs-cli.ts` (git og gh på maskinen) og `vcs-isogit.ts` (isomorphic-git, uten git-installasjon). Testet i `core/*.test.ts`, isomorphic-git mot en lokal `git http-backend`
- `server/kravPlugin.ts` kobler `core/` til Vite: `virtual:krav*`-modulene, Vites watcher og websocket, og middlewares for `POST /__krav/focus` og `POST /__krav/api/<kall>` (bare fra vieweren selv, sjekket med `Origin`). `VCS=isogit` bytter til isomorphic-git-backenden
- `src/markdown.ts` + `src/MarkdownView.tsx` viser `.md`-filer formatert (overskrifter, nestede lister og sjekklister, sitater, skillelinjer, kodeblokker med «Kopier», tabeller, lenkekort, frontmatter, og fet, kursiv, gjennomstreket og `kode` i teksten; testet i `src/markdown.test.ts`), med bryter til rå markdown. Relative lenker til filer i vieweren åpnes internt
- `server/parse.ts` parser med `@cucumber/gherkin` til modellen i `shared/model.ts`, og sjekker konvensjonene i `krav/README.md` (importert i `.claude/rules/gherkin-conventions.md`). Reglene som sjekkes er merket *(sjekkes automatisk)* i README-en, og testes i `server/parse.test.ts` (`npm test`). Bruddene vises som et statusbånd («Fila følger ikke konvensjonene») under metalinja i feature-visningen, og som `!` i treet. **Hold dem i synk:** endres en merket regel, eller kommer det en ny regel som kan sjekkes, skal `parse.ts`, testene og merkingen i README-en oppdateres i samme endring, og omvendt. Framgangsmåten står i `.claude/rules/krav-readme-parser-sync.md`, som lastes når Claude jobber med README-en eller parseren
- `shared/rules.ts` har ID, alvorlighetsgrad (feil/advarsel), README-seksjon og forklaring for hver regel parseren sjekker. Hvert avvik (`Lint`) har `rule` og `sev` derfra
- **Avvik**-modusen (`#/avvik`, bryteren «Krav | Avvik» i toppfeltet) er et dashbord over avvikene i hele `krav/`, portet fra designet «Gherkin Viewer v2» (Claude Design): nøkkeltall, avvik per regel, status og prioritet, «Regel × mappe» med drill-down, fil- og regeldetaljer med «Kopier agent-prompt», og lista over filer med avvik. Klikk på et avvik åpner fila på linja, og «Les regelen» hopper til seksjonen i README-en. Aggregeringen er rene funksjoner i `src/health.ts` (testet i `src/health.test.ts`), visningen i `src/Avvik.tsx`. Rettes et avvik i editoren, viser statuslinja «↻ … rettet i …»
- **Tavla «Oppgaver»** (`#/oppgaver`, tredje knapp i «Krav | Avvik | Oppgaver») er stedet oppgaven flyter: ett kort per oppgavemappe i `tasks/` fra den opprettes (`fs-scope` eller «+ Ny oppgave») til kravene er verifisert. Portet fra designet «Spesifikasjoner» (Claude Design, runde 1, og detaljpanelet fra runde 4), med oppgavekort i stedet for spesifikasjonskort; den gamle Oppgaver-visningen (mappe, faser, gate og review) er fjernet, og `Fase` i `oppgave.md` og `roadmap.md` leses ikke. Kolonnene (`columns`, `FIXED_COLS`, `COL_WHY` i `src/specboard.ts`) er I scope, Kravarbeid og Spesifiseres (de tre svarer til `fs-scope`, `fs-krav` og `fs-specify`, og utledes fra kravene, `DERIVED_COLS`), Klart til utvikling, én per repo (fs-plattform, fs-admin, min-kompetanse, og repoene som står i en rute; `BOARD_REPOS`), Til verifisering og Verifisert; «Kolonner» gir nytt navn, skjuler, flytter og legger til eller fjerner repo-kolonner (`kravforvaltning:specCols` i localStorage). Kolonnen utledes alltid (`taskColOf`, reglene står under *Tavla* i `tasks/README.md`): med spesifikasjoner som ikke er verifisert, den tidligste av dem (`colOf` per spesifikasjon: Verifisert når kravene er `@implemented` eller verify-rapporten har alt funnet, ellers det første repoet på ruta som ikke er levert, ellers Til verifisering, ellers Spesifiseres med det `missing` gir, eller Klart til utvikling); ellers fra kravene uten spesifikasjon (`kravCol`: alle er skjeletter eller finnes ikke → I scope, noen er `@draft` → Kravarbeid, ellers Spesifiseres med «Mangler spesifikasjon»); og Verifisert når alle spesifikasjonene er verifisert og alle kravene (unntatt `@wont`) har spesifikasjon eller er levert. Kravene oppgaven har (`kravFor` i `src/scope.ts`) er scope-raden når oppgaven har `Scope:`, ellers kravene i spesifikasjonene, ellers mappa i «Krav (Gherkin)» (ikke en lenke til et helt domene). Kortet (`TaskCardView` i `src/Tavle.tsx`) viser domene, scope, Jira-saken (`Issue` i `oppgave.md`, `parseIssue` i `shared/tasks.ts`: en Jira-nøkkel som `BAT-268`, eller `#143` for et GitHub issue i oppgaver fra før; initiativet er fortsatt et GitHub issue), antall krav og spesifikasjoner, ruta og steget for spesifikasjonen i samme kolonne, hva som mangler, framdriften i verifiseringen og flaggene (`flags` per spesifikasjon og `taskFlags`: krav uten spesifikasjon, krav utenfor scope-raden, krav i et annet scope eller uten `@scope`, «scope endret» etter at en spesifikasjon ble sendt, krav som ikke finnes, avvik i mappa, ikke merget). Et kort kan dras mellom kolonnene bare når oppgaven har én aktiv spesifikasjon (`dragSpec`, `canDrop`/`moveTo`); de utledede kolonnene kan ikke velges. Filtrene er domene, scope, repo og «tatt av»; de huskes (`kravforvaltning:tavleFilter` i localStorage) til «Nullstill filtre». Detaljpanelet (`src/TaskDetail.tsx`) viser status og neste steg: kolonnen, scope, Jira-saken og eieren, og boksen «Neste steg» (`nextStep` i `src/specboard.ts`, som gir hva som mangler eller skjer nå, fra kravene eller den ledende spesifikasjonen `leadSpec`, og knappene velges fra `kind`: «Kjør fs-scope», «Kjør fs-krav» (`kravPrompt`), «Kjør fs-specify» (`taskSpecifyPrompt`/`specifyPrompt`), «+ Ny spesifikasjon», «Sett rute og send», «Utfør i <repo>», «Utfør med team», «Kopier prompt» (`handoffPrompt`) og «Verifiser»), kravene med en opptelling per status (`kravSummary`) og merker (skjelett, `@wont`, annet scope, uten `@scope`, ingen spesifikasjon), spesifikasjonene som rader (kolonne, rute eller hva som mangler), og avvikene i mappa og scope-fila og statusloggen sammenfoldet. Et krav i panelet åpnes i Krav med `onOpenKrav(path, from)`, og så lenge et av kravene i oppgaven er åpent, viser Krav båndet «← <oppgave>» (`src/TaskBackBar.tsx`, `kravFrom` i `main.tsx`) med kolonnen og filtrene på tavla, som tar deg tilbake til oppgaven. En spesifikasjon åpnes i et bredt panel over tavla (`SpecDetail`, `Drawer`), merket «Spesifikasjon», med faner for spesifikasjonene i oppgaven; klikk utenfor panelet eller Esc går tilbake til oppgaven. Til venstre redigeres tittel, `## Omfang`, kravene (velgeren «+ Legg til krav» med Fuse-søket over filer og mapper i `krav/`, kravene i scope-raden først, og krav i et annet scope merket; hele krav plukkes, `pickable`: `@planned`, levert med åpne deler, eller `@deprecated`), skisser (eller «Ingen skisse: grunn») og åpne spørsmål, og til høyre, under «Utføring», hva som mangler, ruta og stegene per repo (status, tatt av, PR, overlevering, blokkert, «Sendt tilbake av fs-verify»), «Verifiser» og loggen. Endringene skrives til spesifikasjonen (`applySpec` i `shared/spec.ts`, som bare skriver om seksjonene som er endret) og til tilstandsfila `tasks/<d>/<s>/utforing.md` (`shared/utforing.ts`, formatet står under *Utføring* i `tasks/README.md`), og sendes med «Lag PR» («N endret · ikke merget» i toppfeltet). «+ Ny spesifikasjon» i panelet fyller ut kravene uten spesifikasjon og skissene fra scope-raden, og skriver `tasks/<dom>/<slug>/spec/spec-<tittel>.md` (med `- **Scope:**` under `## Kilde`, `newSpecText`) når utkastet har tittel (`kravforvaltning:specDraft` til da). «+ Ny oppgave» i toppen skriver en minimal `oppgave.md` fra malen (`newOppgaveText` i `shared/tasks.ts`). «Kjør fs-specify» og «Verifiser» sender `specifyPrompt`/`verifyPrompt` til Claude-panelet (eller kopierer dem), «Kopier prompt til <repo>» gir `handoffPrompt`, og «Utfør i <repo>» starter en utførekjøring i panelet (under). Ved «Verifiser» velges «Ta skjermbilder (test-fsadmin)» (`kravforvaltning:verifyScreenshots` i localStorage, `src/verifyScreenshots.ts`), og `verifyPrompt` får linja fra `screenshotLine` (`src/verifyPrompt.ts`), så `fs-verify` ikke spør. Uten linja spør `fs-verify` med `AskUserQuestion`. Adressen, `https://test-fsadmin.sikt.no/`, står i skillen. Resultatene per scenario kommer fra `## Scenarioer` i `spec/verify-*.md`. Ruta er `#/oppgaver/<dom>/<slug>[/<spec-fil>]` (med spesifikasjonen er det brede panelet åpent), `#/oppgaver/<dom>/<slug>/ny` og `#/oppgaver/ny-oppgave` (`src/tavleHash.ts`, testet i `src/tavleHash.test.ts`); de gamle `#/spesifikasjoner/…`, `#/oppgaver/tavle/…` og `#/oppgaver/mappe`, også i `kravforvaltning:hash`, gjøres om til de nye (`normalizeHash`). `server/tasks.ts` leser rådataene, også scope-filene `tasks/<d>/scope-*.md` (`virtual:krav-tasks`, pushes som `krav:tasks`), og `shared/tasks.ts` tolker `oppgave.md` (med `Scope`) og scopene (`parseScope`, `buildScopes`) og sjekker reglene i `tasks/README.md` (`taskLint`, `scopeLint`, merket *(sjekkes automatisk)*, testet i `shared/tasks.test.ts`). Hold `tasks/README.md` og `shared/tasks.ts` i synk på samme måte som krav-README-en og parseren. Rene funksjoner i `src/specboard.ts` (`buildBoard`, `buildTaskCards`, `taskColOf`, testet i `src/specboard.test.ts`), `src/scope.ts` (`scopeLinks`, `kravFor`, testet i `src/scope.test.ts`), `shared/spec.ts` og `shared/utforing.ts` (testet i `shared/spec.test.ts` og `shared/utforing.test.ts`), visningen i `src/Tavle.tsx`. Gating-settet (`gating`) holdes i synk med `fs-verify`. Vieweren kan skrive og lage PR av `tasks/<d>/<s>/utforing.md`, `tasks/<d>/<s>/oppgave.md`, `tasks/<d>/scope-*.md` og `tasks/<d>/<s>/spec/spec-*.md` (`isSpecPath` og `isEditablePath` i `shared/paths.ts`, brukt av `core/save.ts`, `checkPaths` og git-lesingen), og lage PR av resten av `tasks/<d>/<s>/spec/` (`isTaskSpecFile`: det `fs-specify` og `fs-verify` skriver, også skissene fra `save_sketch`, `isSketchPath`), ellers bare filer under `krav/`
- **Menyvalg** (portet fra designet «Menyvalg», Claude Design): tannhjulet rett etter «Krav | Avvik | Oppgaver | Flyter» i toppfeltet (`MenuGear` i `src/TopBar.tsx`) velger hvilke visninger som vises i menyen. Krav og Flyter er alltid med («alltid»), Avvik og Oppgaver er skjult som standard (`MENU_DEFAULT`), og skrus av og på (`MenuShow`, `kravforvaltning:menu` i localStorage). Skjules visningen brukeren står i, går visningen til Krav. En lenke eller hash til en skjult visning virker fortsatt. Lukkes med klikk utenfor eller Esc
- **Flyter** (`#/flyter`, fjerde knapp i «Krav | Avvik | Oppgaver | Flyter», portet fra designet «Flyter», runde 1, Claude Design) viser flytene i `krav/_Flyter` og relasjonene deres. Ruta er `#/flyter` (startsiden) og `#/flyter/<sti>[?nivåer=2|3|alle]` (`parseFlyterHash`/`flyterHash` i `src/flows.ts`); nivået står i ruta når det ikke er 1, og ellers i `kravforvaltning:flowDepth` i localStorage (ruta vinner). Flyten som velges, blir også fila i Krav. Til venstre er et eget tre over prosessene og flytene (oversiktsflyten øverst, med eget ikon), skjult med samme knapp som filtreet, og til høyre fasene med status (samme knapp som innholdspanelet). Startsiden har nøkkeltall, flytene per prosess med fremdrift og egen status, og varslene. Den valgte flyten har hodet med «Fremdrift» (fra kravene fasene bygger på, og kjedestatusen: den laveste statusen i kjeden til valgt nivå) og «Flytens egen status» (fra taggen) hver for seg, kjente brudd (`# Kjent brudd:` under beskrivelsen), varslene som gjelder hele flyten, åpne spørsmål og «Brukes i» (oversiktsflytene som bygger på flyten). Verktøylinja har fanene, «Nivåer» (1, 2, 3, Alle, med antall krav per nivå) og «Følg» («Bare delen fasen bygger på», standard, eller «Hele kravet»). Delen er ankeret (*Anker* i `krav/README.md`): reglene og scenarioene i kravet med `@ref-<ID-en over>`, der ID-en over er flyten eller kravet over i kjeden (`anchors` på `Krav`, `focusOf`, `Focus` på `DepNode`). Uten anker er delen regelen i «…» i kommentaren under taggen, når den er en regeltittel i kravet, og ellers hele kravet. For et scenario følges også `@depends-on-` på regelen over (`inFocus`). «Fasene» er en tidslinje (oversiktsflyten en svømmebane), med kortet for hvert krav fasen bygger på, treet med kjeden under (et krav som er vist før, blir en lenke, og ringer stopper treet), henvisningene (`@ref-`), åpne spørsmål og overleveringene (scenarioene, sammenfoldet til `Gitt` og `Så`). «Kravene i flyten» er kravene uten duplikater med nivå, faser, «via» og andre flyter, «Per domene» samler dem per domene og sub-domene, og «Matrise» viser hvor mange krav som gjenstår per sub-domene og fase. Klikk på et krav åpner det i Krav (på delen fasen bygger på, `focusLn`), og en flyt i en fase åpner den flyten. I Krav har metalinja «Vis flyten» på en flyt og «Med i N flyter» på et krav en flyt bygger på (`flowLink` i `FeatureView`). Fremdriften og nivåene regnes som i `fs-verify`: en fase er levert når alle kravene (og flytene) den bygger på, er `@implemented`, en fase uten krav teller med i totalen, hvert krav tas med én gang på det laveste nivået, og `@ref-` følges ikke. Hele krav som er levert, skilles fra regler og scenarioer som er levert (`deliveryOf` og `isPartial` i `src/flows.ts`): er egenskapen `@implemented`, er alt levert unntatt delene som er `@planned` eller `@in-progress`; er den `@in-progress`, bare delene som er `@implemented` (*Delvis levert* i `krav/README.md`); `@draft`-, `@deprecated`- og `@demo`-delene er ikke med. Fremdriften viser krav levert som helhet og regler levert, et krav som er delvis levert, merkes «delvis levert», «Kravene i flyten» har kolonnen «Levert», og matrisen teller bare krav: `@depends-on-` peker på hele kravet, så et krav gjenstår til hele kravet er levert. Regler telles ikke som det flyten trenger: ankeret og regeltittelen under taggen sier hva som følges og vises, ikke når kravet er levert. En fase er fortsatt bare levert når kravene er levert som helhet. Varslene (fase uten krav, brutt referanse, avviklet krav, flyten bak kravene, flyt på flyt på tvers av prosesser, ring og kjente brudd) regnes alltid med alle nivåer og hele kravet. Alt regnes i rendereren fra snapshotet, så visningen virker også på GitHub Pages. Rene funksjoner i `src/flows.ts` (`buildFlows`, `flowTree`, `flatKrav`, `flowWarnings`, testet i `src/flows.test.ts`), visningen i `src/Flyter.tsx`, og klassene `fl-*` i `theme.css`. Skillene i Claude-panelet er `fs-krav`, `fs-scope`, `fs-krav-avvik` og `fs-verify`
- **Utførekjøring** («Utfør i <repo>» på tavla): en egen samtale i Claude-panelet (`target` på samtalen og i `claudeRun`, `execute` i `src/claudeBridge.ts`) der `claude` kjører med kode-repoet som arbeidsmappe, så repoets `CLAUDE.md`, innstillinger og skills gjelder (`--setting-sources user,project,local`). Kravrepoet får `--add-dir`. `executeArgs` i `core/claude.ts` tillater lesing, `Skill` (unntatt kravrepoets egne skills), `Edit(//<kode-repo>/**)` og `Edit(//<kravrepo>/tasks/*/*/utforing.md)`, og Bash bare for `EXECUTE_BASH` (bygge, teste, `git add`/`commit` lokalt); `git push` og `gh` avvises med `--disallowedTools`. Som i panelet går resten til `approve` (`PERMISSION_ARGS`), som spør brukeren om WebFetch og serverne i `MCP_SERVERS` og avviser alt annet; `--mcp-config` har serverne i `MCP_SERVERS` fra `~/.claude.json` og appens egen (uten `save_sketch`), og kode-repoets egen `.mcp.json` lastes som vanlig. Stien er klonen under «Kodemapper». Systemteksten (`implementPrompt`) har spesifikasjonen og protokollen for `utforing.md`. Skillvelgeren og «Kodemapper» skjules i en slik samtale
- **Terminalen** (agent teams): agent teams kan bare startes i en interaktiv `claude`-økt, ikke med `-p` (panelet) eller Agent SDK. «Utfør med team» ved «Utfør i <repo>» på tavla, «Verifiser i terminal med agent team» ved «Verifiser» der, og «I terminal med agent team» i «Verifiser»-menyen på egenskapen starter derfor interaktiv `claude` i en pseudo-terminal (`core/pty.ts`, `PtyRunner`, med node-pty), vist med xterm.js i Claude-panelet (`src/TerminalView.tsx`, en samtale med `terminal` i `src/claudeChat.ts`, `terminal` i `src/claudeBridge.ts`). Til `ptyStart` har svart, viser panelet «Starter Claude Code i en terminal …» med spinner (`starting` i `ClaudePanel`), og til claude har skrevet noe, ligger «Starter Claude Code og kobler til MCP-serverne» over terminalen (`waiting` i `TerminalView`). Brukeren sender selv. I Krav og Oppgaver kan Claude lese kodeklonene `fs-admin`, `fs-plattform` og `min-kompetanse` (`CODE_DIRS` i `shared/api.ts`, «Kodemapper» over inputfeltet, `src/CodeDirs.tsx`), som `fs-verify` trenger. Standardstien er `KRAV_FS_ADMIN` / `KRAV_FS_PLATTFORM` / `KRAV_MIN_KOMPETANSE`, ellers mappa ved siden av repoet (`codeDirs` i `core/claude.ts`, kallet `claudeDirs`). Stien kan overstyres i panelet (`kravforvaltning:claudeDirs` i localStorage). Desktop-appen har ingen standardsti ved siden av repoet (det er appens egen klone): brukeren velger sine lokale kopier med mappevelgeren (`pickDir`), og appen laster ikke ned kode-repoene. Uten valgte kodemapper er `fs-verify` gråtonet i desktop-appen. Mapper som finnes, får `--add-dir`, og `Edit(//<sti>/**)` i `--disallowedTools`, så Claude kan lese koden, men ikke endre den. Uten Bash kan ikke `fs-verify` slette filer i panelet; den sier hvilke, og brukeren sletter selv. Claude bruker brukerens egen innlogging
- **«VS Code»** i toppfeltet åpner repoet i VS Code (som `code .`) i et nytt vindu, med lenken `vscode://file/<sti>?windowId=_blank` (`vscodeUrl` i `src/vscode.ts`, testet i `src/vscode.test.ts`). Stien er `repoRoot` i `Boot`: `ws.repoRoot` i desktop-appen, `virtual:krav-root` i dev-serveren, og `null` i statisk bygg, der knappen skjules. Electron sender `vscode:`-lenker til `shell.openExternal`
- `src/transport.ts` er rendererens eneste forbindelse til backenden: Vites websocket og `fetch` i dev, snapshotet bakt inn i statisk bygg, og IPC via `window.krav` (preload) i desktop-appen. `main.tsx` venter på `transport.boot()` før den tegner
- **Desktop-appen** (`electron/`, `electron.vite.config.ts`, `electron-builder.yml`): electron-vite 6 (beta, fordi stabil 5 ikke støtter Vite 8). Electron-programmet lastes ned av `postinstall` (`scripts/electron-install.mjs`, som kjører `node_modules/electron/install.js`), fordi npm 11 med `allow-scripts` ikke kjører installasjonsskriptet til Electron, og da feiler `npm run app:dev` med «Electron uninstall». Ved første oppstart klones `sikt-no/fs` (grunn klone av main) til appens datamappe med isomorphic-git, så brukerne trenger ikke git. «Hent siste» henter main og oppdaterer filene som ikke er endret lokalt, og fjerner mappene som blir tomme når filer er slettet på main (git har ikke tomme mapper, og tavla viser ikke oppgavemapper uten filer, `readTasks` i `server/tasks.ts`). Appen sjekker ved oppstart, hvert tiende minutt og når vinduet får fokus om main på GitHub er nyere enn klonen (`mainStatus` i `vcs-isogit.ts`, som bare leser refs). Er den det, hentes antall commits, endrede `.feature`-filer under `krav/` og siste forfatter fra GitHub compare (`compareCommits` i `core/vcs.ts`; feiler kallet, vises banneret uten tallene). Er alle de endrede filene i appen selv (`fs-kravforvaltning/`, `onlyAppChanges` i `core/vcs.ts`, testet i `core/vcs.test.ts`), varsles det ikke: kravene er de samme, og appen oppdaterer seg fra releasene. Endringene hentes med neste endring i kravene. Da vises banneret «Det finnes en ny versjon av main» under toppfeltet (`src/MainBanner.tsx`, tekst og synlighet i `src/mainStatus.ts`, testet i `src/mainStatus.test.ts`), og knappen «Ny versjon av main · Hent siste» i toppfeltet. «Senere» skjuler banneret til main får en ny commit (`kravforvaltning:mainLater` i localStorage). Mens «Hent siste» pågår, viser knappene en spinner og kan ikke klikkes. Innloggingen bruker device flow og krever en OAuth-app i `sikt-no` (`KRAV_GITHUB_CLIENT_ID` ved kjøring, eller `MAIN_VITE_KRAV_GITHUB_CLIENT_ID` ved bygg). Tokenet lagres kryptert med `safeStorage`. `KRAV_REPO=<sti>` bruker en eksisterende klone i stedet for appens egen. Appen oppdaterer seg selv fra GitHub-releasene med electron-updater (`electron/updater.ts`, bare i den pakkede appen): ved oppstart og hver fjerde time finnes den nyeste releasen med tagg-prefikset `fs-kravforvaltning-v` (`latestReleaseTag` i `shared/appUpdate.ts`, testet i `shared/appUpdate.test.ts`; «Latest» i repoet brukes ikke), og `latest-mac.yml` i den leses med `provider: generic`. En nyere versjon lastes ned i bakgrunnen, og main sender `krav:app-update`. Da vises kortet «FS Kravforvaltning <versjon> er lastet ned» nede til høyre, over statuslinja (`src/UpdateToast.tsx`, `.updatetoast` i `theme.css`, portet fra designet «Oppdateringsvarsler», 1c, Claude Design: main har båndet, appen kortet, så de ikke forveksles), med «Senere» og «Start på nytt» (`installUpdate` i preloaden; editoren lagres først). «Senere» skjuler kortet for den versjonen (`kravforvaltning:updateLater` i localStorage, `updateToastShown` i `shared/appUpdate.ts`), og legger knappen «<versjon> Start på nytt» i toppfeltet (`.apppill`, `appUpdate` i `TopBar`). Versjonen installeres uansett når appen avsluttes. En versjon som ble lastet ned før vieweren var tegnet, hentes med `updateDownloaded`. Statuslinja viser versjonen (`desktop-app · v<versjon>`, `VITE_APP_VERSION` fra `electron.vite.config.ts`). `KRAV_UPDATE_URL=<url>` henter oppdateringen fra en annen mappe, for å teste lokalt (se `docs/release.md`)

## Prosesser

Stopp aldri prosesser etter navn eller mønster: ikke `pkill -f vite`, `pkill node`, `killall electron` eller lignende. Brukeren har som regel sine egne dev-servere og Electron-apper i gang, også FS Kravforvaltning som desktop-app, og de stoppes da også.

- Stopp bare prosesser du har startet selv: den bakgrunnsoppgaven du startet (stopp oppgaven), eller PID-en du fikk da du startet den (`kill <pid>`).
- Er porten opptatt (5173 for dev-serveren, 5273 for desktop-appen i dev, begge med `strictPort`), er det brukerens server. Bruk den, eller spør. Stopp den ikke.
- Ikke stopp prosesser ut fra en port (`lsof -ti :5173 | xargs kill`). Porten kan tilhøre brukeren.
